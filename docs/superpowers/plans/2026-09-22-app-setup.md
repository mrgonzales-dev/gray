# App setup in `/gateway` — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Setting up an app (Discord first) is one flow inside `/gateway`: the app says what it needs, gray asks for exactly that, verifies it, registers the app's tool, and starts the daemon — no dead-end wizard, no TTY requirement, no systemd assumption, no budget quiz.

**Architecture:** A declarative `setup` block per app (v1: in core's `CATALOG`) feeds a registry that computes per-app state; `/gateway`'s manager loop gains one optional per-row setup action; the flow reuses the connect-modal entry pattern (masked secrets), writes the app's config atomically, runs the app's own verify command, then registers and starts. Listens on hermes-agent's model (reference/NousResearch/hermes-agent): plugin declares credentials → core registry → masked prompt with portal URL → presence = enabled → per-init restart.

**Tech Stack:** Rust workspace (`crates/gray`), ratatui/crosstterm for the modals, reqwest (already a dependency) for the Discord channel picker, `tempfile` for tests.

**Spec:** `docs/superpowers/specs/2026-09-22-app-setup-design.md`

## Global Constraints

- Secrets never appear in logs, error strings, Debug output, or anything sent to the model. Config files are written dir `0700` / file `0600`, atomically (temp + rename).
- No new top-level command: interactive surface is `/gateway`; headless is `gray gateway setup <app>`.
- No budgets anywhere in the setup path.
- Every task is TDD: failing test first, then the minimal implementation, then the full `cargo test -p gray`, then commit.
- Formatting/lints: `cargo fmt --check` and `cargo clippy --workspace -- -D warnings` clean before each commit (CI gates on both).
- Fast loop per AGENTS.md: `cargo test -p gray` while iterating; `./target/debug/gray` for manual checks.
